# nw — Network Devices

Network-devices fleet spoke. Repo: `nw`. `module_type = "nw"`. See [architecture-topology.md](architecture-topology.md).

## Role & module_type

Manages a **fleet** of switches/gateways (one spoke → many devices). Per-device discovery (probe, device info, MAC table, ARP, interfaces) over SSH/CLI, REST, or SNMP. Source for the NW→NetBox discovery sync (ARP attributed to tenants by IP-prefix containment) and the per-device POLL NOW inventory sync.

## What it does

nw manages a **fleet** of switches and gateways from a single spoke — unlike most LM modules (one spoke per target system), one nw spoke can hold many devices (AOS-Switch, AOS-CX, Juniper EX, Aruba/HPE gateway). It logs into each device to pull device info, MAC address tables, ARP tables, and interface lists, then feeds that data into NetBox so the network topology (devices, IPs, MACs, cabling) shows up automatically instead of being hand-entered.

In the WebUI this is the **Network Devices** view (Setup → Network Devices tile for adding/editing devices; the module tile itself reads "Network Devices (nw)"). Live fleet state (reachability, per-device MAC/ARP/interface data) is shown wherever the Network Devices page renders a device row.

## Entrypoints

`python3 -m src.control_plane` (`NwControlPlane`); spoke `NwSpoke(BaseSpoke)`, module name `"nw"`. systemd `lm-nw.service`. Installer `install_nw.sh` (clones to `/opt/lm/nw`, venv, `.env`, unit; equals-attached `--id=…` form so values starting with `-` don't trip argparse; clears `SPOKE_SECRET` to `""` when unset for zero-touch pending).

> **Primarily a role now.** nw runs mainly as the **`network`** role hosted by the agent (`agent-<hostname>`, unit `lm-agent`): the agent opens a sub-spoke `{agent}-network` (module_type `nw`, parent-auto-approved) and self-installs it via `agent/src/agent_spoke.py::_install_role` (clones `lbockenstedt/nw.git` + deps). The dedicated `lm-nw.service` / `install_nw.sh` `nw-spoke-1` path is the **legacy/standalone** alternative. The device fleet still arrives via the hub push (`global_config["nw_devices"]` over `UPDATE_CONFIG`), not a per-module `.env`.

## Ports / backends

No port served. Per-device transports (chosen by `object_type` + `transport`):
- **SSH/CLI** (`SshCliDriver`, `transports/cli_io.py`, asyncssh + per-vendor text parsers): AOS-Switch (`aos_switch`, default ssh), Junos EX (`ex_switch`, ssh). `enable_secret` enters enable mode on AOS-S.
- **REST** (`RestDriver`, `transports/rest_io.py`, httpx): AOS-CX RESTv1 basic auth (`cx_switch`, default rest), Aruba/HPE gateway REST bearer (`gateway`, default rest). TLS verify controlled by `LM_NW_VERIFY_TLS` (default off).
- **SNMP** (`SnmpDriver`, `transports/snmp_io.py`, pysnmp-lextudio, SNMPv2c): valid for any family.
- Vendor command map in `_VENDOR_COMMANDS` (`aos_switch`, `cx_switch`, `ex_switch`, `gateway`).

## Environment variables

`SPOKE_ID`, `SPOKE_SECRET`, `HUB_SECRET`, `HUB_URL`; `LM_NW_VERIFY_TLS` (rest_io). The fleet itself is **not** env-driven — the hub pushes `global_config["nw_devices"]` via `UPDATE_CONFIG` on connect/approve/reconnect.

## Install flags

`install_nw.sh`: `--hub`, `--id`/`--name`, `--secret`, `--hub-secret`, `--all-prereqs` (no-op).

## Key commands / handlers (`nw_spoke.handle_command`)

`UPDATE_CONFIG` (store fleet, masked, returns `device_count`), `GET_VERSION`, `NW_LIST_DEVICES` (fleet summary + concurrent 3s probe per device for live reachability), `NW_PROBE`, `NW_GET_DEVICE_INFO` (optional `address` probes the fleet device's credentials against another IP — used by the hub's stub-merge live poll), `NW_PING_SWEEP` (ping-first sweep for the hub's scan option), `NW_GET_MAC_TABLE`, `NW_GET_ARP`, `NW_GET_INTERFACES`, `NW_GET_ENDPOINTS` (fused ARP+MAC unique IP/MAC list), `NW_GET_VLANS`, `NW_GET_LLDP_NEIGHBORS` (per-port neighbour detail — chassis id, remote port, system name, management IP — the topology map's primary feed), `NW_POLL` (probe + device_info + interfaces + arp + mac_table in one call; each sub-call independent → partial results + `errors`), `NW_RUN_CONFIG` (TODO/not-implemented envelope — config push out of scope), `NW_SCAN`/`NW_DISCOVER` (fingerprint scan — hub sends candidate target IPs + vault-overlaid scan credentials + options; the spoke probes and returns identified manageable devices, mutating no fleet state), `INSTALL_CERT` (hub-brokered LE cert install on a fleet device). MACs canonicalized to lower-colon `aa:bb:cc:dd:ee:ff` on the way out.

**Unsolicited pushes (spoke → hub).** Beyond command replies, the autonomous loops push `NW_POLL_RESULT` (a completed per-device data poll, so the hub warms its cache without being asked) and `NW_REACHABILITY` (the ICMP sweep verdict, so the fleet up/down badge stays fresh between the hours-apart data polls).

## Object types and identity (recent)

- **`ipmi` object type** — iLO / iDRAC / IPMI / BMC / AMT, SNMP by default; wired through add, import and scan paths and shown as an IPMI category tab. The scanner classifies BMCs from SNMP `sysObjectID` / `sysName` and `hpilo` banners.
- **Vendor-neutral BMC identity** — SNMP OID tables and web probes read serial, host server model and MAC (HPE serial MIB, iLO `xmldata`, iLO 4 TLS accepted; SNMP "No Such Object" text is never taken as a serial). The host model sizes the server's rack unit.
- **Switch/gateway identity** — chassis serial, base MAC, model and firmware for CX (`show system`), AOS-S (`show system`, `show modules`) and gateways (`show inventory`, HW MAC / VLAN 1 SVI); SNMP uses the SKU model, ENTITY-MIB serial and BRIDGE-MIB base MAC. These feed NetBox matching and stub merging.
- **Scanner** — retries sysName once, keeps open ports when identify times out, returns a probe profile for hosts it cannot identify, records SNMP-only hosts as monitor-only, and promotes the answering address when a device's primary went silent.
- **Poll schedule** persists across restarts (first poll within minutes).

## Key files

`src/nw_engine.py` (~1,270 lines — `NwEngine`, `NwDriver` base + `SnmpDriver`/`SshCliDriver`/`RestDriver`, `build_driver`, `_norm_mac`, `_VENDOR_COMMANDS`, `_DEFAULT_TRANSPORT`), `src/transports/{cli_io,rest_io,snmp_io}.py` (lazy-imported so the engine imports cleanly without asyncssh/pysnmp) plus `src/transports/vtscreen.py` (screen-scrape/pager handling) and `src/transports/device_profile.py` (per-vendor profile resolution), `src/nw_scanner.py` (`NwScanner` — the `NW_SCAN` fingerprint/identify engine; TCP-probe + SSH/SNMP identify + optional nmap augment, probe steps injected so it unit-tests without a network), `src/nw_poll_scheduler.py` (`plan_poll_tick` — pure cadence math: interval resolution, first-sight spread, anti-resonance jitter, per-tick dispatch cap), `src/nw_spoke.py`, `src/control_plane.py`, `install_nw.sh`, `API_SPEC.md`.

## Notable behaviors & gotchas

- **Driver selection** — `transport=auto` resolves per `object_type` (aos_switch→ssh, cx_switch→rest, ex_switch→ssh, gateway→rest). Unknown `object_type` → driver None, device skipped.
- **Failure isolation** — every driver method returns a `{"status":"ERROR",…}` envelope (never raises); `poll()` continues on partial failure; `list_devices` probes concurrently with `asyncio.gather` + 3s `wait_for` and falls back to `unknown` reachability so the UI never shows a stale "up".
- **Logging** — `_log_datum`/`_log_result` emit INFO on success (row count) and ERROR (carrying "error" so it surfaces in the hub `GET_ERROR_LOGS`/Error Log tab). Credentials (`password, enable_secret, api_token, snmp_community, secret, hub_secret`) never logged.
- **ARP is the discovery feed** — `NW_GET_ARP` data is what the hub's NW→NetBox sync attributes to tenants by IP-prefix containment and pushes via `NETBOX_SYNC_DEVICES`; `NW_POLL`'s `interfaces` feed `NETBOX_SYNC_NW_DEVICE`.
- **Autonomous loops** — `start_background_loops()` runs a data-poll loop (per-device `poll_interval`, 6h default) and an ICMP reachability sweep (fleet-wide `ping_interval`, 5m default, `0` disables), both 10s-tick, idempotent and process-scoped. Started by the standalone control plane **and** by the agent's `RoleConnection`, so a role-hosted nw polls and pings too. They push `NW_POLL_RESULT`/`NW_REACHABILITY` unprompted; anti-stampede math lives in `nw_poll_scheduler.plan_poll_tick`.
- **Scan agent is allowlisted** — `NW_SCAN` only ever runs on an nw spoke bound to the requesting tenant or to the shared tenant. No "any connected spoke" fallback (see "Network discovery scan" below).
- **Cache lives on the hub, not here.** The spoke is stateless across commands apart from the in-memory fleet (`self.devices`) and the background loops' scheduling state; there is no JSON cache file on this spoke. Hub-side `NwCacheMixin` (`lm/core/src/nw_cache.py`) caches the nw fleet + per-device info/macs/arp/interfaces in memory AND atomically persists `cache/nw_data.json` (loaded on startup to seed the Network Devices UI on restart/spoke-outage). Staleness sweep lives on the **netbox** spoke (`NETBOX_STALENESS_SWEEP`).
- **LLDP has two consumers with different contracts.** The scanner's crawl uses `parse_lldp_neighbors`, which returns a plain `List[str]` of management IPs to enqueue as scan targets. The topology map uses `parse_lldp_detail`, which returns full neighbour records. They are deliberately separate: widening the crawl's return type to satisfy the map would change what every scan caller receives. Dedup lives in the `parse_lldp_detail` wrapper rather than inside each vendor layout parser, because the worker has three return paths and a newly-added vendor layout would otherwise silently skip it.
- **A chassis id is not always a MAC.** LLDP chassis subtypes can carry an interface name or a locally-assigned string. `_norm_chassis` only canonicalizes values that actually look like a MAC — naively normalizing `OLKS-CORE` to `olks-core` invents a second identity for a switch already on the map.

## How it works

- **Fleet delivery, not per-device install.** The device list is never read from a file on the spoke — the hub pushes the whole fleet as `global_config["nw_devices"]` via `UPDATE_CONFIG` every time the spoke connects, is approved, or reconnects, and again any time an admin adds/edits/deletes a device in the WebUI. The spoke's `NwEngine.set_devices()` just replaces its in-memory list; there is no per-module `.env` involved in device data.
- **Driver selection per device.** Each device dict carries `object_type` (`aos_switch`, `cx_switch`, `ex_switch`, `gateway`) and `transport` (`ssh`, `rest`, `snmp`, or `auto`). `auto` resolves per `object_type`: `aos_switch`/`ex_switch` → SSH/CLI (asyncssh + vendor text parsers in `transports/cli_io.py`), `cx_switch`/`gateway` → REST (httpx, `transports/rest_io.py`; AOS-CX RESTv1 uses basic auth, Aruba/HPE gateway REST uses a bearer token; TLS verification is controlled by `LM_NW_VERIFY_TLS`, off by default). SNMP (`transports/snmp_io.py`, SNMPv2c) is valid as an explicit transport for any device family. An unrecognized `object_type` builds no driver at all — the device is silently skipped (logged as a WARNING), not errored.
- **Commands the hub can send:** `NW_LIST_DEVICES` (fleet summary + a concurrent 3s-timeout reachability probe per device — this is what powers the up/down dot in the UI), `NW_PROBE`, `NW_GET_DEVICE_INFO`, `NW_GET_MAC_TABLE`, `NW_GET_ARP`, `NW_GET_INTERFACES` (each a single per-device datum), and `NW_POLL` (all four data pulls plus a probe in one call — this is what "POLL NOW" in the UI triggers). `NW_RUN_CONFIG` (pushing config changes to a device) is a stub today — it always returns a not-implemented error envelope, it does not silently no-op.
- **Failure isolation.** Every driver call returns a `{"status": "SUCCESS"|"ERROR", ...}` envelope; a transport exception is caught and turned into an ERROR envelope rather than raised. `NW_POLL` treats its four sub-pulls independently, so one failing datum (say ARP times out) doesn't blank out the others — the response carries whatever succeeded plus an `errors` list, and its overall status is `PARTIAL` rather than `SUCCESS` if reachable but any sub-datum errored.
- **Data flow into NetBox** happens in two distinct paths, both hub-orchestrated (the sync logic itself lives on the hub, not the nw spoke):
  - The **discovery sync** (`nw_discovery_sync.py`) periodically calls `NW_GET_ARP` (and `NW_GET_MAC_TABLE`) against every device on every connected nw spoke, merges the results, attributes each IP↔MAC pair to a tenant by IP-prefix containment, and pushes per-tenant to the netbox spoke via `NETBOX_SYNC_DEVICES` (`source="Network Devices"`, `replace=True` — so a nw-owned tenant's record set is fully replaced each cycle, without touching records other sources like opnsense discovered). IPs matching no tenant prefix are dropped and counted, not created as orphans.
  - **POLL NOW** on a single device (`poll_nw_device`) runs `NW_POLL` against that device, attributes it to a tenant by its own management-address prefix containment, and pushes the device + its interfaces to NetBox via `NETBOX_SYNC_NW_DEVICE` — a `dcim.device` inventory upsert, distinct from the ARP-based `NETBOX_SYNC_DEVICES` flow above.
- **Network discovery scan (`NW_SCAN`).** The hub aggregates a tenant's candidate host IPs (`_aggregate_scan_targets` in `lm/core/src/routes/nw.py`: NetBox tenant prefixes expanded to hosts, plus NAC endpoints / DHCP leases / DNS records from that tenant's bound spokes, plus any explicit subnets/targets — deduped, IPv4-only, capped) and sends them with the chosen scan-credential sets (vault secrets overlaid just before the push) to an nw spoke. `NwScanner` TCP-probes the common management ports, then tries SSH and SNMP identify with each candidate credential and classifies each reachable target into an `object_type` family. Unknown targets are reported but never auto-added. **Scan credentials are optional**: with none selected the scan runs as a *discovery-only* pass (every candidate IP is TCP-probed for reachability + open management ports, and `use_nmap` is defaulted on so service detection can still classify a host) — it simply cannot SSH/SNMP-identify. Since auto-add only ever fires for a target classified into a manageable `object_type`, a credential-free scan cannot mutate the fleet. The response carries `reachable` (hosts that answered but were not identified) and `discovery_only`, both rendered in the Scan tab. On a non-dry-run the hub adds the newly-identified devices to the tenant fleet tagged `source="scanned"`, carrying the winning credential set's vault reference so future fleet pushes overlay the same secret. Each device added this way is then **polled immediately as part of the discovery** (background, `_nw_poll_discovered`, same path as POLL NOW): its MAC/ARP/LLDP/interface data is cached, its display name is reset to the hostname read off the box, and its inventory is pushed to NetBox — it does not wait for its first scheduled `poll_interval` poll.
- **Known hosts are checked every scheduled scan; every responder lands in NetBox; SNMP responders land in Zabbix.** `_aggregate_scan_targets` puts known hosts first: every IP NetBox records for the tenant (or its tenant group) plus every host in the seen-hosts registry. `_execute_nw_scan` pings all targets (`NW_PING_SWEEP`) before the TCP/SNMP scan, then sends hosts that answered ping but not the scan to a `pinged` `NW_SCAN` follow-up (sweep ports + vault SNMP; unprofiled first, 1024 max). Responders from scans and the sweep are recorded in `gc["nw_seen_hosts"][tenant]` (`lm/core/src/nw_seen_hosts.py`, kept 37 days) and pushed to NetBox as `NETBOX_SYNC_DEVICES` (`source="Network Sweep"`, `replace=False`, IP-keyed, hostname + probe `profile` so the netbox spoke can guess a role); fleet devices are skipped. Only hosts that answered SNMP with a tenant vault credential within 24h join the Zabbix inventory (`inventory_devices`); fleet devices also need verified SNMP (`snmp_ok`, or a seen-hosts entry for one of their addresses). The scanner never adds ping-only hosts, and the Zabbix spoke deletes any ping-only host LM no longer sends. A seen host joins only under its SNMP sysName: one whose sysName is already monitored is the same box at another address (a switch SVI/gateway) and is skipped, as is one with no sysName; the Zabbix spoke deletes old hosts named by bare IP once LM stops sending them. To monitor any other address, use the **Monitor** toggle on IPAM → IP Addresses (`PUT /api/monitoring/watch`, stored in `gc["monitoring_watch"][tenant]`): it is polled over SNMP when verified, otherwise by ICMP ping, until toggled off. A host that stops answering stops being pushed, so NetBox tombstones it (offline at 7d, deleted at 30d; revived if it answers again) and Zabbix ages it out on the same clock. `GET /api/nw/sweep` returns `unidentified`: registry hosts with no hostname or type yet, with their ports/SNMP/profile evidence, so a human or AB can work out what they are.
- **Background supernet sweep (opt-in per tenant, Network → Scan).** A NetBox prefix wider than /22, or one that contains other prefixes, is a *supernet*; scheduled scans only expand the other (leaf) prefixes. Every ~3 min the sweep does one batch (`_nw_sweep_step` in `lm/core/src/routes/nw.py`): (1) **gateway pass** — pings `.1` and `.254` of each /24 in the supernets that has no NetBox prefix (`NW_PING_SWEEP`, 1024 /24s per tick) and adds every /24 whose gateway answers to NetBox in the tenant's VRF ("Found by LM gateway sweep"), so scheduled scans cover it; reruns weekly or on "Find subnets now"; if every /24 in a batch answers, nothing is added (a device answering for any address). (2) **host sweep** once the pass is done — skips everything the directed 6h scan already covers (leaf prefixes, the tenant's saved scan subnets, DNS/DHCP/NAC hosts, fleet devices and seen-hosts registry IPs) and pings the remaining space 1024 addresses per tick and sends only the hosts that answered to `NW_SCAN` (TCP 22/23/80/443/830/4343/8080/8443 plus SNMP with the tenant's vault communities; `pinged` makes SNMP run even with no open TCP port). Every host that answers is recorded in the seen-hosts registry (below). The Scan tab shows only a found-host count and whether the sweep is running (`found`/`running` on `GET /api/nw/sweep`).
  - **Which agent runs the scan is tenant-scoped.** The allowlist is the tenant's OWN nw spokes plus any bound to the shared tenant (`nw_scan_spoke_choices`); `resolve_nw_scan_spoke` prefers an own connected agent, else a connected shared one, and a requested `spoke_id` outside the allowlist (e.g. a stale global `nw_scan.spoke_id`) is ignored rather than trusted. There is deliberately **no** "any connected nw spoke" fallback — that previously made an admin's scan of tenant A run on whichever single nw agent happened to be online (tenant B's), so the targets were aggregated for one tenant and probed from another tenant's vantage point. With no own/shared agent connected the scan returns an actionable 503 instead of borrowing a foreign one. The tenant Scan tab renders this allowlist as a **Scan Agent** picker (own vs shared, offline entries disabled).
  - **Credentials are the tenant's own.** The chosen credential sets are narrowed to ones owned by the scanned tenant or the shared tenant for every caller, including a full admin — a scan always runs with that tenant's vault credentials.
- **Caching lives on the hub, not the spoke.** The nw spoke itself is stateless between commands (aside from the in-memory fleet and the background loops' own scheduling state). The hub-side `NwCacheMixin` (`lm/core/src/nw_cache.py`) caches the last fleet list and each device's info/MAC/ARP/interfaces/poll result in memory, and atomically persists them to `cache/nw_data.json`. On hub restart this file reloads and seeds the Network Devices UI immediately (and it continues serving last-known data if the nw spoke is offline) instead of the page 503ing until the spoke reconnects.
- **Scheduling.** Three independent cadences:
  - The hub-side **discovery sync** runs on its own configurable loop (`nw_netbox_device_sync` in global config: enabled/source/mode/interval — the loop starts ~75s after hub startup, staggered after the firewall-discovery sync so both don't fire simultaneously).
  - The spoke's **autonomous data poll** (`NwSpoke._nw_poll_loop`) ticks every 10s and polls any device whose `poll_interval` has elapsed (module default `default_poll_interval`, else 6h), pushing `NW_POLL_RESULT` so the hub warms its cache unprompted.
  - The spoke's **ICMP reachability sweep** (`NwSpoke._nw_reachability_loop`) ticks every 10s against a fleet-wide `ping_interval` (default 5m; `0` disables), caches the verdict on the engine so a box confirmed DOWN isn't hammered with a full SSH/SNMP/REST poll, and pushes `NW_REACHABILITY`.

  Both spoke loops are started by `start_background_loops()` (idempotent, process-scoped, survives hub reconnects) from **both** the standalone `NwControlPlane.run_hub_mode` **and** the generic agent's `RoleConnection._start_role_local_services` — so a role-hosted nw actually polls and pings. They idle until the control-plane back-ref reports a live hub connection. Anti-stampede (jitter + per-tick dispatch cap + a concurrency semaphore) lives in `nw_poll_scheduler.plan_poll_tick`. POLL NOW remains available on demand on top of all this.

## How to use it

- **Add a device to the fleet.** Setup → Network Devices → "+ Add Device". Required fields: a name, `object_type` (AOS Switch / CX Switch / EX Switch / Gateway), `transport` (leave `auto` unless you need to force SSH/REST/SNMP), the device's management `address`, and credentials appropriate to the transport (SSH: username/password/`enable_secret` for AOS-S enable mode; REST: username/password or API token; SNMP: community string). Saving pushes the updated fleet to the connected nw spoke immediately via `UPDATE_CONFIG` — no spoke restart needed.
- **Check whether a device is reachable.** The Network Devices list view itself triggers `NW_LIST_DEVICES`, which live-probes every device (3s timeout each) — reachable/unreachable/unknown shows per row.
- **Pull live data for one device.** Open the device's detail row and use Poll Now — this runs `NW_POLL` (probe + device info + interfaces + ARP + MAC table in one call) and immediately also pushes the device to NetBox via `NETBOX_SYNC_NW_DEVICE`.
- **View the MAC or ARP table.** From the device detail view, the MAC Table / ARP tabs pull `NW_GET_MAC_TABLE` / `NW_GET_ARP` directly (fresh, not from cache) — MACs are always shown canonicalized as lower-case colon-separated (`aa:bb:cc:dd:ee:ff`).
- **Trigger a discovery sync to NetBox on demand** instead of waiting for the scheduled interval: use the "Sync now" action on the nw discovery card in System → Sync — this pulls ARP from every device on every connected nw spoke and pushes to NetBox right away.
- **Discover devices you haven't added yet.** Network → Scan (tenant-scoped; admin or tenant-admin). Pick the **Scan Agent** (your tenant's own nw agent, or a shared one if offered), tick the scan-credential sets to try, choose the IP sources (NetBox prefixes / NAC / DHCP / DNS) and optionally add extra subnets or targets (a target may be a host IP, a CIDR such as `10.0.0.0/24`, or a range such as `10.0.0.10-20` — all are expanded to host IPs, bounded by the target cap), then **Preview scan** to see what would be found without touching the fleet, or **Scan & add** to add the identified devices. A recurring schedule for the same scan lives on the card below it. It is **on by default** (every 6 hours, first run ~10 minutes after the tenant's nw spoke appears) and adds what it identifies; the tenant can change the interval/subnets or tick **Preview only** (`dry_run`) to report without adding. With no credential set ticked, every set the tenant owns is tried. The last run time persists, so a hub restart resumes the cadence.
- **See the scans that are already scheduled.** `GET /api/nw/scan-schedules` lists every configured recurring scan across the tenants you may see (a Global Admin sees all tenants; a tenant-admin only their own), narrowed to the selected tenant when one is picked (`?tenant=`), with the cadence, dry-run flag, scan agent, credential sets and IP sources it will use, plus the scheduler's last run / next due / last outcome. The runtime fields are in-memory on the hub: a restart clears them and every schedule re-defers one full interval (anti-stampede), so a null `last_run_at` means "not since this hub started", not "never". A schedule with no credential sets selected is flagged `discovery_only`.
- **See the network map.** Network → Topology (tenant-scoped). Links are drawn by provenance and the distinction matters: **solid slate = LLDP** (both ends advertised the adjacency — a fact), **solid green = declared** (a human asserted it), **dashed amber = inferred from MAC tables** (where an endpoint is attached — a *guess*, see below). Untick "Infer links from MAC tables" to see only links something actually asserted. The page builds from the hub's warm per-device cache without touching the devices; **Refresh from devices** gathers LLDP + MAC tables live from every device in the tenant (bounded concurrency) and is the slow path.
- **Infrastructure-only by default; collapse to declutter.** The map opens showing **infrastructure only** — nw fleet switches/gateways, operator-declared devices, and anything with a real hostname corroborated by NetBox, its own LLDP advertisement, or a management IP (TORs, PDUs, UPSes, Proxmox/iLO hosts). Nodes known only by a MAC, NetBox's auto-discovered `device-<mac>` placeholders and garbled LLDP names count as endpoints and are hidden; tick **Show endpoints** to include them. The API marks each node with `infra` (and `stats.infra_nodes`), so the classification is the same everywhere. Every node with children shows a **−/+N** badge: click it to collapse/expand that branch. Click a **Level N** column header to collapse/expand every node at that level, or use **Expand all / Collapse all**. Collapse state is kept per tenant across refreshes.
- **Where each endpoint is plugged in.** Every MAC in a polled switch's MAC table is placed on the port where it is physically attached. A MAC is learned on every switch between it and the poller, so sightings on an uplink toward another *polled* switch are ignored (that switch reports the real port). Of the remaining ports, the one with the fewest MACs wins. When that port faces a device that is on the map but not polled (a TOR, a Proxmox host advertising LLDP), the endpoint hangs off that device ("behind 1/1/40"). Switches' own MACs and nodes that already have an LLDP/declared/NetBox link are not re-linked. MAC-only endpoints are named by their MAC and are never written to NetBox as cables. With **Show endpoints** ticked, each device's endpoints fold into one **N endpoints** node; click it to list them (each link is labelled with its switch port), click again to hide them. **Expand all** opens every group; **Collapse all** closes them. AOS-CX switches are read with `show mac-address-table` (columns MAC/VLAN/Type/Port). AOS-CX learns MACs on the LAG (`lag251`) while LLDP names the physical member (`1/1/51`); a LAG is tied to the LLDP neighbour whose own chassis MAC appears on it, so everything learned on that LAG hangs off that neighbour (e.g. the TORs behind TOR-AGG). A host that advertises its NIC MAC as the LLDP port id is matched on that MAC too, and a NIC firmware's own LLDP agent (a free-text name like "Broadcom P225p …" with a sibling MAC of the host on the same port) is folded into the host instead of appearing as a device. Interfaces come from `show interface brief` (singular — the AOS-S `show interfaces brief` is rejected by CX).
- **VSX pairs and stacks are one logical device.** Two polled switches cabled to each other that also have at least two devices dual-homed on the *same* port number of both (MCLAG wiring) are drawn as one switch named `CRSW1 / CRSW2`. Its tooltip lists the members, every link is labelled with the member that owns the port (`CRSW2 1/1/51`), and the ISL between them is kept on the unit (`isl`) instead of drawn. A VSF or backplane stack already answers as one device; its member numbers are read from its ports (`9/1/52`, `10/1/52`) into `stack_members` and shown in the tooltip. NetBox cables from a VSX unit are still written against the physical member switch. Fleet copies of a switch found on a VRRP/active-gateway VIP are folded into whichever member actually answers (its LLDP table proves it), and the VIP's possibly wrong scanned name is ignored.
- **Put a device that doesn't speak LLDP on the map.** Network → Topology → "Devices that don't speak LLDP" (admin / tenant-admin). Declaring a name plus its **MAC** is usually enough: the MAC is matched against every switch's MAC table, and the port that learned it becomes an inferred link automatically. Where that can't work — the port is a trunk carrying a whole downstream segment, or the device is behind an unmanaged switch — declare the link explicitly instead; the ends may be given as a device id, name, IP or MAC. Declared devices and links persist per tenant under `global_config.nw_tenant_cfg[<tenant>].topology` and always win over an inferred link on the same port.
- **Edit or remove a device**: Setup → Network Devices → edit/delete on the device row; the change is re-pushed to the spoke the same way as an add.

## Troubleshooting / common questions

- **"A device shows unknown or unreachable in the Network Devices view — is it actually down?"** `NW_LIST_DEVICES` probes each device with a 3-second timeout; `unknown` means the probe itself errored (not necessarily that the device is down) while `false`/red generally means the connection attempt failed outright. Check: is the management `address` correct, are the credentials for the configured `transport` correct, and is the device reachable on the network from wherever the nw spoke/agent runs (SSH/443/SNMP port open, no ACL blocking it). A probe failure is logged at WARNING (not ERROR) during a fleet list, since one device being briefly unreachable in a big fleet is normal.
- **"The nw spoke/agent shows offline (red) in Diagnostics — what happens to the Network Devices page?"** Nothing breaks — the page continues to show the hub's last-known cached fleet + per-device data from `cache/nw_data.json` (see NwCacheMixin above). New probes/polls simply can't run until the spoke reconnects; expect stale (not empty) data.
- **"I added a device but it doesn't show up / doesn't get polled."** Confirm the object_type is one of the four supported values — anything else silently skips the device (logged as a WARNING: "Unknown object_type ... — skipped"), it will not appear as an error to the user, just missing from results. Also confirm a nw spoke (or an agent's `network` role) is actually connected — devices sit in `global_config["nw_devices"]` but nothing polls them without a live spoke.
- **"I tried to push a config change to a switch and nothing happened."** `NW_RUN_CONFIG` (config push) is not implemented yet — it deliberately returns an error envelope ("run_config not implemented for this transport") rather than silently doing nothing, so this is expected behavior today, not a bug.
- **"I ran a scan while in one tenant but the results are another tenant's devices."** That was a real bug, now fixed. Two causes: the spoke resolver had an "any connected nw spoke" fallback that picked whichever nw agent was online (another tenant's) when the current tenant's agent was offline, and the Setup-card scan sent no tenant so the server fell back to the shared tenant. Scans are now constrained to the tenant's own or an explicitly shared agent, and the WebUI sends the active tenant. If you see a 503 "No connected Network Devices agent for this tenant" instead, that is the fix working — check Diagnostics for your tenant's nw spoke/`network` role being offline, deploy nw in the tenant, or pick the shared agent in the Scan Agent dropdown.
- **"The Scan Agent dropdown is empty / says no agent is deployed."** Nothing is bound to your tenant and there is no shared nw spoke. An nw spoke bound to no tenant at all is admin-only and deliberately never offered (an unassigned spoke attributed to every asking tenant would put the same fleet on every tenant row). Bind the spoke to the tenant in Setup → Module Management.
- **"Why does NetBox show a device from nw discovery that I don't recognize, or why did a nw-discovered device disappear?"** The discovery sync is authoritative per cycle for nw-owned records: each run replaces the tenant's ARP-discovered device set with what it just saw (records not seen this cycle are deleted, but only ones previously tagged as nw-owned — other sources' records like opnsense's are untouched). A device that stopped showing an ARP entry (e.g. it aged out or the switch was unreachable that cycle) will disappear from NetBox on the next sync. A device whose management IP falls outside every tenant's NetBox prefixes is dropped from the push entirely (logged as an unattributed count), not created as an orphan.
- **"The topology map is missing links I know exist."** In order of likelihood: (1) the devices at each end don't run LLDP, or don't run it on that port — declare the link by hand; (2) the port is a **trunk/uplink**, listed in the "Trunk / uplink ports" table below the map. A port carrying many MACs tells you a whole segment is downstream but says nothing about what is *directly* attached, so the map deliberately refuses to guess there; (3) the far end isn't a device the map knows, so an inferred link would have nowhere to land — declare the device (a MAC is enough); (4) the per-device cache is cold or stale — hit **Refresh from devices**.
- **"A host / VM I expect isn't on the topology map."** The default view is infrastructure only. A node that has only a MAC, or only NetBox's `device-<mac>` name, is classed as an endpoint and hidden; tick **Show endpoints**, or give the device a real name in NetBox so it counts as infrastructure. Also check that no collapsed node (a **+N** badge) is hiding it.
- **"The topology is a mesh of MAC / `x86_64` / IP-named nodes instead of my switch tree."** Two causes, both fixed. (1) nw did not understand real AOS-CX `show lldp neighbor-info detail`, whose remote fields are prefixed `Neighbor` (`Neighbor Chassis-Name`, `Neighbor Port-ID`, ...). The text fell through to column parsers that turned description lines into neighbours with local port `:`. Similarly, the AOS-8 gateway `Capability` column (`B:R`) was read as the remote port. Update nw, then **Refresh from devices**. (2) The scanner adds a switch once per address it answers on (each SVI, the VSX virtual IP), so one switch appeared as several `172.21.x.y` nodes. The hub now merges fleet entries that report the same set of real LLDP neighbour ports (chassis + port, at least two) into one node, and a real hostname learned from LLDP or NetBox replaces an IP-literal name. A device in the fleet only by IP (a gateway scanned as `172.21.2.3`) takes the name its neighbour advertises for it: when the gateway says `GE0/0/2 → 1/1/43` and the core switch says `1/1/43 → GE0/0/2 MIPBE-SSPLM-N31-VPNC1`, both rows describe the same link, so the gateway is VPNC1 and the link is drawn once.
- **"I moved an NW agent to another tenant and its devices stayed in the old tenant."** Device records follow the tenant that finds them, once the old record is *unanchored* — its agent now belongs to a different tenant, or was deleted — and the sighting is verified. A record is moved (same id; `moved_from` records the old tenant/agent, time and evidence; logged as `nw: moved device …`) when (1) a scan by the new tenant identifies it at the same IP with the same hostname, or the same agent sees it at the same IP; (2) its moved agent polls it at its address and the hostname or chassis serial matches; or (3) another tenant's record polls the same chassis serial (or, both serial-less, the same base MAC and hostname) — the stale row is folded into the live one as `alt_addresses`. A move adopts the scan credential that authenticated to the device, re-pushes both agents' fleets, and re-polls the device so NetBox/Zabbix follow. Records whose agent still belongs to their tenant, or that sit in the shared tenant, never move — two tenants that both see a box can't bounce it back and forth; IP alone (tenants overlap address space) is never enough. Explicit preview scans list candidates as `move_preview` without moving them. A scan into a tenant group (e.g. `group:ssplm`) treats its member tenants' NetBox prefixes as its own, so those addresses are no longer skipped as another tenant's. In Zabbix the moved device's existing host is re-keyed (technical name, `LM/<tenant>` group, proxy) instead of a second host being created; a tenant group without a proxy of its own is monitored through a member tenant's proxy (the former tenant's first) and uses the members' SNMP vault secrets.
- **"Setup → Module Management lists the same switch several times."** A switch answers SSH/SNMP on every SVI and loopback, so older scans added it once per address. NetBox and Zabbix already used one row per box (grouped by chassis serial, else hostname + type, per tenant). Click **Merge duplicates** (admin; `POST /setup/nw-devices/dedupe`, dry run first). It keeps the row NetBox and Zabbix use and stores the other addresses on it as `alt_addresses`. A row is removed only when a poll confirms it is the same box: same serial, or the same base MAC when neither has a serial. Same-name rows that no poll has confirmed are listed and left alone. Scans now skip known `alt_addresses`; a host whose hostname and type match an existing device is recorded as another address of it instead of a new entry.
- **"I do not see any cables in NetBox."** LLDP is written to NetBox as cables by `NETBOX_SYNC_LLDP`. The hub sends it after every nw discovery sync cycle, after each successful poll (including scan-added devices), and on Topology **Refresh from devices**. It sends the same merged graph the map draws, with every identity of each end (name, MACs, IPs, fleet id). NetBox matches by MAC first and by name only last, ignoring case and the domain suffix. A neighbour NetBox has never seen (a switch or server known only from LLDP) is created as a `discovered` device with its UPPER-CASE short hostname. Device names in NetBox are always upper-case. The hub log shows `nw lldp->netbox tenant=...: N links: X cabled, ...`. Nothing is written while the NetBox role is down (the topology page shows NetBox inventory *unavailable*).
- **"Switches / servers I can see in `show lldp neighbor-info` are missing from the map while NetBox shows *unavailable*."** Fixed: a neighbour with a real hostname learned from LLDP now counts as infrastructure on its own; earlier it also needed NetBox or a management IP. Only the neighbours of fleet devices are visible, so the switches *below* a TOR aggregation switch appear only once that switch is in the nw fleet (Setup → Network Devices or Network → Scan) or NetBox has its cables.
- **"A device I declared isn't showing up / isn't connected to anything."** A declared device with no MAC and no declared link has nothing to attach it to — it appears as an isolated node by design. Give it a MAC that the upstream switch has actually learned, or declare the link explicitly. Check the MAC really is in the switch's MAC table (device detail → MAC Table); a device that has been silent long enough to age out of the table can't be inferred.
- **"Everything in the topology is a single dot / the map is empty."** Under the ADMIN (`default`) tenant the map is intentionally empty and prompts you to pick a tenant — a topology is only coherent within one tenant's slice, so the ADMIN scope does not aggregate across tenants. Select a specific tenant from the tenant picker.
- **"Network → Scan shows no scan credential sets even though I have credentials in the Vault."** Two different things. A Vault entry holds the *secret*; a **scan credential set** is a separate object that merely references it, created on Setup → NW Scan Credentials — Vault entries alone never populate the picker. Second, a credential set added while bound to an nw spoke is automatically stamped with **that spoke's tenant**, and the Scan tab is per-tenant, so the set only appears when that tenant is selected in the tenant picker. Under ADMIN (`default`) the tab now prompts you to choose a tenant rather than rendering an empty picker and writing scan settings to a tenant bucket nothing reads.
- **"Is nw running as its own service or as part of the agent?"** In the current topology, nw normally runs as the `network` role inside the generic `lm-agent` unit (sub-spoke `{agent}-network`, auto-approved by its parent) — check Diagnostics for a spoke id like `agent-<hostname>-network`. The standalone `lm-nw.service` / `install_nw.sh` path (spoke id `nw-spoke-1`) still works but is the legacy path; either way, device config always arrives via the hub push, never a local `.env`.
